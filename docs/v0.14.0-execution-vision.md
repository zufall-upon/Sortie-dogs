# v0.14.0 — judgment at entry, autonomy in execution

## Product vision

The Operator uses the original instruction and already available conversation context to recommend an initial executor. It does not investigate the repository or environment merely to classify the work. The Coordinator treats that recommendation as a useful starting point, starts useful work immediately, and may implement directly or delegate remaining work as actual execution makes that choice useful.

Success means accepted user outcomes with fewer avoidable reads, repeated investigations, handoffs and model turns. It does not mean fewer capabilities, less demanding work, narrower acceptance, hidden failures or a higher apparent completion rate.

## Execution policy

- Explicit user choices govern. Otherwise, clear bounded implementation and known procedures normally suit the configured Worker; coupled design, ambiguous requirements and cross-system integration normally suit the Coordinator. These are judgment cues, not a scoring form, hard threshold or mandatory classifier call.
- Make the initial recommendation from existing information, with a short reason when useful. Task length, file count and availability of a validation command do not alone decide difficulty.
- The Coordinator can investigate, design, edit, validate and deliver substantial work in its existing session. It is an implementation owner, not a dispatch-only role. It does not repeat the Operator's assessment as a preliminary investigation.
- Necessary source/environment investigation belongs to the actual work. Continue directly while that is efficient; delegate when the remaining work is clearer or separation reduces effort. A change of approach is normal execution, not an approval request.
- Preserve useful work and context across delegation. Transfer remaining action, exact original requests, observed failures and current validation facts. Do not restart discovery just because the actor changes.
- A recommendation is not an immutable requirement, a permission grant or acceptance evidence. Existing user requirements, host authority, real command outcomes, applicable review and final acceptance still determine success.
- A direct-to-Worker handoff is a continuation of the same unit, with retained authorship and cumulative accounting. A live command must finish before its writer ownership is transferred; handing off partial work is neither a successful check nor an implementation failure.

## Implementation and acceptance

1. Persist optional `preferred_executor` and expose it in the Coordinator brief/status. Honor it at the initial dispatch even when a known single unit is supplied. Existing calls without it remain readable and usable.
2. Align Operator/Coordinator instructions, tool descriptions and host next actions. No model-facing route should quietly restore mandatory Worker-first behavior after a Coordinator recommendation.
3. Support yielding the current direct unit through the existing planning API. Keep Mission/unit identity, source changes, formal observations and budget reservation; retire the old writer before admitting the Worker. Resume after process reload without duplicate dispatch or settlement.
4. Exercise real edits, command exits, continuation, cancellation/reload and final acceptance in the existing public harness. Use current successful source-bound checks rather than manufacturing evidence or repeating unchanged work.
5. Validate one integrated candidate with related tests, the mandatory full suite and an actual CLI task. Record actual executor/model, outcome, time, cost and any remaining blocker separately from configuration or startup success.
