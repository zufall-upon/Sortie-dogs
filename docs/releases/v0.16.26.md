# v0.16.26 — Nested validation scratch

## Changes

- Resolve explicitly configured validation scratch relative to the individual check's working directory, including a nested checkout. Generated scratch no longer invalidates that check solely because its directory differs from the Location.
- Continue to protect declared inputs, tracked inputs, and exact outputs. Refresh and Review rediscover tracked inputs for the captured validation working directory, including newly tracked files; older bindings keep their original scratch recipe.
- Reuse the scoped tracked-file discovery from #384 and disable `core.fsmonitor` for those scans. A Git subdirectory Location still scans its own tracked files even when its `.git` is in an ancestor.

The execution recovery, validation evidence, Coordinator default and concise reports from #384 were already delivered in #385 and v0.16.25; they are not reapplied here. The older stale-evidence record did not retain a per-file snapshot diff, so this change does not establish its unique cause.

## Review disposition and deferred work

- #384's tracked-file protection finding for a Git subdirectory Location is valid; the Location scan is retained and covered alongside the nested-checkout cases.
- Its fsmonitor finding applies to the introduced tracked-file scans; the existing #384 override is included for these scans, without claiming to secure all Git operations.
- The `.git/info/attributes` compatibility finding concerns #384's private filterless Review implementation, which is not included here; that implementation's behavior is neither adopted nor claimed fixed.
- The redirected-metadata and nested Git Review content findings, the recursive submodule/filterless Review work, and broader Git hardening remain deferred. The user did not request that work as a condition of this integration. The pre-existing behavior and the synthetic reproduction described in the v0.16.25 notes are not claimed fixed.
