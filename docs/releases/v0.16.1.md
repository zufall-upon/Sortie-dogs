# v0.16.1 — Nested repository review and conversation recovery

- Resolve declared Review outputs against their nested repository or linked worktree before invoking the outer Git. Keep narrow file/directory scopes narrow; unrelated inner sources and Git metadata are not candidate outputs. The Mission root's baseline is not applied to a different repository.
- Keep background settlement inspection errors recoverable without rejecting the next prompt, model context or compaction. Report the failed inspection and next action; retain the native terminal, cumulative accounting and pending reconciliation. Failure is not validation, Review PASS or final acceptance, and does not authorize repeating an already successful external operation.
- Preserve strict errors for broken repositories and missing Git objects. Ordinary tool admission and explicit acceptance checks are unchanged.

## Evidence and limits

- Three new regression cases first failed on the previous implementation: narrow directory/file outputs expanded to an entire ignored worktree, and a settlement error rejected the follow-up prompt. All 140 related Review, background lifecycle and V2 adapter tests passed after correction.
- A read-only replay of the original saved npm-publish Mission/run/scopes reproduced `git ls-files: internal error - directory entry not superset of prefix` on v0.16.0. The corrected inspector returned in approximately 251 ms. Original Mission/run/publication receipt hashes were unchanged; the recorded publish attempt count remained one. This replay made no model request and did not resume or accept the original session.
- The release gate binds one integrated main commit and one tarball/SHA-256 before candidate preflight, mandatory full tests and actual native Worker/model startup. Use that same archive for global/config-local application, GitHub Release and npm publication. Startup does not prove Mission completion or official benchmark correctness. No shared OpenCode service is restarted automatically.

Command/exit/timing, review dispositions, package hashes, startup usage and publication evidence are retained under `_testenv/releases/0.16.1/`. The shared host's loaded version and original session continuation remain separate from installed-byte verification.
