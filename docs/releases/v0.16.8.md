# v0.16.8 — Register queued requests without reopening terminal goals or resetting spend

## Included changes

- Integrates PR #332, source head `43e61ccb291d74702dbdc7697eba359952417c99`. A separately queued real user request received before Goal A finished can now register as Goal B after A's formal success, rather than attempting an invalid revision of A's terminal state.
- A limited `goal.queued-accepted` event binds the exact settled predecessor receipt, unchanged budget, current Mission and unused native request. The normal root/user-message/content/timing checks and pinned prepared-run controls remain in force. Ordinary new-goal acceptance remains a separate budget lineage.
- Consumption of units, time, cost and validation budget is derived from the prior state. For example, 28 consumed units out of 32 remain 28/32, not 0/32. A's receipt, original records, attachments, failures and evidence remain unchanged; A's passing evidence is not B's acceptance proof.
- An interruption after acceptance or before Mission/run binding reuses the same prepared run. Late native usage from A can reconcile once into the shared queued budget using the exact goal/reservation/native-session identity, without rewriting A's receipt or accepting another request.
- Existing ledger formats, immutable blob storage, locking/hash chain, normal scope revision, current writer protection, cancelled-direct-writer release, compact background notifications and history/debrief callers remain supported. Older reducers reject the new cross-goal event instead of silently resetting consumption; use this compatible runtime for histories containing it.
