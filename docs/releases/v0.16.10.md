# v0.16.10 — Useful early parallel Scout discovery

## Changes

- Restore early, concrete repository discovery instead of waiting for a proven blocking evidence gap. Fast-first Operator, Mission Coordinator and canonical routing share one policy: zero Scouts when existing evidence or direct work is sufficient, one for one useful question, and two or three independent useful questions in one parallel foreground round. No mandatory-three ritual, extra Coordinator or preparation unit.
- Scout uses native Read/Glob/Grep to follow relevant callers and tests. Known paths become seeds/search areas rather than a four-path read allowlist. Remove the 120-line, one-read-per-path and 800-character instruction limits; retain eight steps, Luna Fast max, existing question codes/four JSON keys and native host permissions. Shell/web/edits/child dispatch remain outside Scout.
- Reuse source path/line facts and unresolved risks in the next Worker's objective/handoff context. Required author source inspection and validation freshness remain legitimate. Discovery is not validation, independent Review or acceptance.
- Early root Scouts now use the existing Mission consultation recording/model/outcome/result/reload path even before an implementation run exists. Existing Reviewer generated-task/source checks, Advisor routing, execution grants, Worker budget and formal root acceptance remain unchanged.
