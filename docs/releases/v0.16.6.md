# v0.16.6 — Preserve large Goal evidence without raising ledger limits

## Included changes

- Integrates PR #329 (`238217f98e0d74bf8e38641a1ceca6e2449b0d9e`). Large valid protected-snapshot evidence can no longer stop public `finish_direct_unit` solely because inline Goal history exceeds the 16 MiB document limit.
- During a successful append under the existing lock, large logical events move into a ledger-specific `<ledger>.blobs` sidecar as immutable, SHA-256-verified chunks of at most 1 MiB. Storage version 0.2 reconstructs complete events and checks the unchanged event hash chain before normal reduction. It does not summarize or discard requirements, original references, validation provenance/freshness, author, cumulative spend or failures.
- Old 0.1 history remains readable. Older writers reject migrated storage under the same lock instead of rewriting an unknown format. Existing index-byte and event-count limits remain; this is not a limit increase.
- Missing, altered or truncated chunks prevent recovery. Failed chunk publication or index replacement retains the previous index and retryable state; unreferenced chunks may remain after a failed write.

## Backup and compatibility

**The ledger and its `<ledger>.blobs` directory are one storage unit.** Back up or move both in a consistent snapshot. Copying only a migrated index is insufficient. A runtime older than this storage implementation cannot read/write migrated history; use a compatible runtime rather than rewriting the version or removing evidence. Real power-loss durability is unverified.
