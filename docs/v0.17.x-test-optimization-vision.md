# v0.17.x — Test optimization vision

**Status: implementation under integration.** The effects on test count, execution time and
defect detection have not been established as general improvements. The scope and limitations
of the candidate are described in the [v0.17.0 release notes](releases/v0.17.0.md).

## Goal and scope

AI-assisted development can accumulate redundant tests, repeatedly run expensive suites
and spend increasing time maintaining checks. The goal is to make test optimization a
standard part of ordinary Sortie-dogs Missions, without requiring a separate cleanup
Mission or another user request. It applies to projects worked on by Missions, not only
to Sortie-dogs itself. Essential regression detection and required validation remain.

## Three connected capabilities

### Test Gate

When tests are added or changed, examine the regression or specification value that
existing tests lack. Prefer improving or combining existing checks when sufficient;
keep necessary behavior, boundary, error, public API and security coverage. The normal
Reviewer considers duplication and weak assertions within the existing workflow, not
a new agent or mandatory extra review round for every test. A test-count ceiling is not
a substitute for quality.

### Test Debt Audit

At appropriate Mission milestones or signs of test growth, inventory available test
information and identify evidence-backed cleanup candidates. Distinguish observations
from unknowns, and compare the specifications, historical regressions and security or
API boundaries that must remain protected. Necessary deeper analysis may supplement
lightweight routine assessment.

For safe candidates, actually apply and validate consolidation or removal, rather than
stopping at a report. Compare the checks and detection results before and after changes;
a passing remaining suite or similar test names alone do not prove that removed checks
had no value. When safe cleanup is not established, leave the checks in place and record
the reason and a later opportunity to reassess. Feed the causes of unnecessary growth
back into Test Gate decisions.

### Full Test Guard

Immediately before a managed long-running test, assess whether to run it, use a narrower
check, defer it or reuse compatible current evidence. After a known failure, start with
the relevant focused check. Evidence reuse requires matching candidate, inputs, scope,
dependencies and environment, not merely the same command name.

Joining an equivalent execution already in flight is distinct from reusing a completed
result. Failures, cancellation, changed candidates and unknown outcomes must not become
success. Required platform, integration, security and release checks remain in place.
Shell and script paths, coverage of the managed execution boundary and bypass handling
need implementation and verification; unsupported paths must not be described as guarded.

## Integration and evaluation

The intended sequence is normal development and Test Gate, milestone assessment and
practical cleanup, freezing the candidate including that cleanup, then Full Test Guard
and the required validation. Milestone detection can be separated from when heavier
analysis or edits run. Do not trigger an unlimited audit loop from the audit's own edits,
invalidate a verified candidate unnecessarily, or rerun full tests unconditionally after
every cleanup. Changed candidates need applicable fresh evidence; valid unchanged results
may be reused only under the existing freshness rules. Respect Mission scope, ownership,
permissions and unrelated local changes.

Incremental implementation and representative runners are reasonable starting points,
but a single test suite or manual cleanup Mission does not complete this vision. The
intended completed behavior connects all three capabilities in ordinary Missions across
multiple projects, with safe cleanup actually performed and duplicate managed executions
prevented. All languages, every runner and universal monitoring inside arbitrary scripts
are not prerequisites for starting work; unsupported cases must remain visible.

Evaluation should state the candidate and conditions, and separately report test count,
new tests, execution time, duplicate starts, optimization overhead, protected behavior
and observed detection results. Neither a fixed reduction percentage nor a speedup is
promised. Specific tools, adapters, thresholds and implementation details remain to be
chosen and checked for suitability and licensing.
