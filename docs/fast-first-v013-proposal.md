# v0.13.x PR proposal: Fast-first Mission

## User problem and target

Sortie-dogs produces useful results but takes too long to return them. For a request that fits one useful Worker unit, the normal path should be Operator → Worker investigation/edit/validation → independent Reviewer **when warranted by the actual change** → Operator acceptance. Coordinator joins only when a real correction or coordination need is known. The measure of success is time to a validated answer, not the share of requests labeled Fast or the time to a Task launch.

This PR starts from v0.12.25 `main`. PR #126 (review excerpt omissions) and PR #127 (aborted orphan settlement) are separate and not treated as integrated speed improvements here.

## Smallest operational change

- Make the existing single-unit `plan_units` route the first choice. A source change, multiple files, an API label, duration or an independent review need do not by themselves require Coordinator. The root must still supply a truthful scope and an exact meaningful formal validation command. If those are not yet available, use Coordinator for targeted discovery; do not invent a dummy validator or dispatch a sacrificial Worker.
- Allow the root to dispatch exactly the host-generated independent Reviewer after its direct Worker succeeds. Use actual `risk_tags`, retain the existing freshness/validation/independence requirements, and keep root final acceptance. Empty tags are for genuinely low-risk work, not a property of Fast-lane.
- Show the current Fast action in `operator_status`: plan an unplanned single unit; review a validated one; wait for a pending Reviewer; accept a reviewed candidate; or start the **same mission's** Coordinator after failure or concrete FINDINGS. Keep completed work and cumulative budget. Never duplicate an active Worker.
- Do not add a router model, security layer, user approval, forced Reviewer for low-risk work, another state machine, or a blanket requirement to retry a failed check. Model assignments stay unchanged.

## Autonomy, efficiency, visibility audit

- **Autonomy:** Worker investigates and validates within its contract; Operator does not approve each unit. On FINDINGS/failed validation/out-of-scope correction, existing Coordinator handles the problem within the same original request. A user-only decision or actual budget expansion still belongs to the user.
- **Efficiency:** routine requests omit the initial Coordinator inference and task round trip. Independent review, when needed, does not add a Coordinator merely to dispatch it. Do not repeat an unchanged check or Review to manufacture proof. The existing contract still requires exact validation before Worker dispatch; relaxing that into Worker-selected late binding is a separate change only if observed wait times justify it.
- **Visibility:** `operator_status` distinguishes Fast planning, validation, pending review, reviewed acceptance and escalation. A Reviewer FINDINGS result is not PASS; EVIDENCE_GAPS at its bounded limit is not a quality score. No extra model call for progress.

## Verification and limits

- Production-hook regression: direct Worker → recorded native validator → host-generated independent Reviewer → succeeded receipt, without a Coordinator. A separate FINDINGS branch asserts the same mission/candidate survives promotion to Coordinator. Mutating the generated Reviewer Task is rejected.
- Full WSL and Windows suites run before PR. A short real-V2 CLI probe, if available, must identify the installed candidate package and actual Worker/Reviewer models; a model-free fixture does not establish real-model elapsed-time savings.
- Follow-up evaluation: matched routine requests on old/new fixed packages, with original requirements, acceptance and models held constant. Record request→first useful edit/check and request→validated completion, p50/p90, Worker/Reviewer/Coordinator count, retries, unresolved gaps, missed defects and estimated cost. Do not infer speed or quality gains from a single heavy Anko run or from a lower inference bill alone. A measured regression sends the route back for repair, not a new per-request gate.

## Real V2 observations (isolated Windows CLI fixtures)

- Windows `.cmd` launch and V2's forward-slash session paths initially broke the *probe*, not the native run. The launcher now uses native npm/OpenCode entrypoints; the observer accepts both path forms. The first probe's DB and project state were reconciled read-only after the path fix. Its original zero-model/zero-cost observation was false.
- Candidate package SHA-256 `9aa19d80924dfa714aee06c7f546a8622385604ac48322bef4a7c10a192297e2`: a low-risk `result.txt` change produced a native succeeded receipt without Coordinator or Reviewer; Worker started at 19.339s, first edit at 46.729s, CLI returned at 103.862s; estimated model cost $0.12728192, no unpriced requests. The skipped Reviewer is appropriate **only** for this low-risk fixture.
- With the same candidate package, a separate multi-file public-logic fixture (`normalizeState` plus positive/negative checks) produced Worker 1 → independent Reviewer `PASS` → succeeded receipt, with no Coordinator. Worker started at 75.895s, first edit at 103.700s, CLI returned at 266.194s; estimated cost $0.15613760, no unpriced requests. External `node check.mjs` also passed. The probe's generic 60s *start-only* threshold made its original `accepted` field false despite native completion; complete-mode acceptance no longer uses that threshold. It remains a useful latency measurement, not a demonstrated speed gain.
- Two matched pairs used the same prompt (SHA-256 `89480f158443c7aaac50e7a584913cb63e504f71015ac045bd5a8a0ed77c9920`), unchanged model assignments, candidate package above and the published v0.12.25 package SHA-256 `b6607f7ca3cbc3b219e878f584fbddf998d3f72b8d9718ddff8a20f1d3a02e3e`. Order was candidate→baseline, then baseline→candidate. Each run had a 360s timeout and an estimated-model-cost cap of $1 in the first pair or $0.50 in the second. All four ran to native succeeded receipts with independent Reviewer `PASS`, one Worker and no retries; a read of not-yet-created `normalize.mjs` failed harmlessly once in each. The external `node check.mjs` passed for all four, and each result rejects invalid states. No official or hidden grader was run.
- Root-session creation→first edit / CLI launch→exit (different clock origins): candidate 103.700s / 266.194s versus baseline 84.144s / 209.615s in pair 1; candidate 53.171s / 136.270s versus baseline 64.388s / 181.320s in pair 2. Candidate had zero Coordinators in both; baseline had one in both. First Worker start relative to root creation: candidate 75.895s and 27.366s; baseline 51.868s and 40.522s. Estimated model cost: candidate $0.156138 and $0.164042; baseline $0.221378 and $0.267661, with no unpriced requests; matched total $0.809219. The separate low-risk probe above adds $0.127282.
- **Decision: keep PR #129 draft.** Pair 1 was 56.579s slower, pair 2 was 45.050s faster. Two pairs on one synthetic fixture cannot establish a causal speed or quality gain, credible p50/p90, or relief for real user requests. The direct route and independent review work in native V2; the latency target remains unproven. Compare representative real requests and investigate Operator/Review idle time before asserting pain relief or removing draft status. Do not turn the probe's start-only 60s condition into a product gate.

## Astra consultation and instruction-only pilot

- Read-only native V2 phase accounting: in the two Fast-first runs above, Worker final response→`review_mission` call was 66.781s and 13.904s; baseline Coordinator runs were 15.149s and 13.804s. Worker and Reviewer inference themselves were similar across Fast-first runs. The first Fast run's focused source reads completed in under a second, so deleting inspection or independent review would not address the measured delay and would weaken quality. `complete_mission` call→final visible response also varied: 34.384s and 20.457s in Fast-first versus 17.574s and 16.763s in baseline. These intervals contain model, host and scheduling time; they are not proven idle time.
- The `start_mission` tool description still said to dispatch the Coordinator immediately, contrary to its Fast-first result. Align the description and clarify the Operator's Worker-result→focused missing-evidence→review→final-acceptance sequence without skipping source inspection, repeating unchanged checks, or adding a turn/approval quota. New fixed package SHA-256 `ecc6cc24e7ecb7ed4ad92c0dbeb4640c89942685d49e6cd4b432f6d49b1239a6`; prior Fast-first package SHA-256 `9aa19d80924dfa714aee06c7f546a8622385604ac48322bef4a7c10a192297e2`.
- One same-prompt A/B, prior package first: 146.205s CLI completion, Worker start 26.117s, first edit 58.647s, Worker→Review 10.097s, estimated $0.173872; new package: 152.807s, Worker start 31.403s, first edit 62.225s, Worker→Review 15.383s, estimated $0.172120. Both retained one Worker, independent Reviewer `PASS`, native succeeded receipt, no Coordinator; the external `node check.mjs` passed on both. The new instruction did **not** show a speed improvement in this pilot. Its consistency fix remains useful but is not a demonstrated latency optimization. No extra Anko or grader run; the six matched model runs spent about $1.155211 under the $2 campaign cap, plus the earlier low-risk probe's $0.127282 outside that campaign.
- Next hypothesis, not yet implemented: measure final report generation and verify V2 host-side panel rendering and CLI visibility before changing model-authored report copying. Do not remove the measured return panels or trade away Review/acceptance to save output time. Prioritize representative real requests with original requirements, first useful work, verified visible completion, rework, quality and cost before draft removal.
