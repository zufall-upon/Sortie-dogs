# Sortie-dogs v0.8 Evidence-Driven Runtime Roadmap

Status: proposed product architecture

## Product thesis

Sortie-dogs v0.8.x compiles intent into a verifiable execution plan, runs that plan on bounded low-cost
lanes, escalates only the work blocking completion, and can explain and replay every control-plane
decision. Completing this line establishes the product foundation for v1.

```text
user intent
    |
    v
Acceptance Compiler -> ExecutionPlan
    |                      |
    |                      v
    |              Content-Addressed Evidence
    |                      |
    v                      v
experience router -> five-lane Luna fabric
                           |
                 +---------+---------+
                 |                   |
          Failure Swarm       critical-path Sol
                 |                   |
                 +---------+---------+
                           |
                           v
                  hidden candidate -> final CAS
                           |
                           v
                    Run Flight Recorder
```

The six capabilities are one evidence-driven loop, not six independent agent personas:

1. Critical-path Sol Escalation rescues only the unit blocking elapsed completion.
2. Experience-driven Auto Router selects Sol or Luna from inspectable local outcomes.
3. Failure Swarm investigates distinct causes in parallel and authorizes one repair.
4. Acceptance Compiler produces the plan that all later controls enforce.
5. Run Flight Recorder makes decisions reconstructible and replayable.
6. Content-Addressed Evidence deduplicates bounded context across lanes and runs.

Routing remains automatic. v1 adds no user-facing model mode, lane count, opaque online learning, or
agent council.

## Foundation in v0.8

The [five-lane Luna execution fabric](speculative-execution-v0.8.md) is the execution substrate:

- Terra decomposes accepted work into an exact dependency DAG.
- Up to five distinct ready units execute concurrently on Luna.
- Unsuitable jobs and demoted units execute on Sol.
- Wave artifacts accumulate in hidden immutable candidate snapshots.
- Final validation and review precede one target compare-and-swap.
- Target state remains unchanged on failure.

Evidence-runtime work starts only after the v0.8 five-lane vertical slice and production RPT pass their
documented go gates.

## Shared architecture

### Evidence Plane

The Evidence Plane owns two primitives used by every later capability.

#### Evidence capsules

An evidence capsule is an immutable, content-addressed, bounded record containing:

- Schema and extractor version.
- Relevant source blob fingerprints and paths.
- Relevant symbols or regions.
- Acceptance item links.
- Known risk facts.
- Validation command and evidence fingerprints.
- Bounded provenance needed to verify freshness.

The capsule key hashes its canonical body. A lane declares capsule hashes in its unit contract and
cannot widen that set itself. Identical evidence resolves once and is reused by concurrent lanes.
Changed relevant source content produces a different key; unchanged relevant blobs remain reusable even
when an unrelated repository path changes.

Capsules contain bounded evidence, not raw logs, secrets, full repository snapshots, or Project
metadata. Workers still read exact authorized source paths when implementation requires source text.

#### Run ledger

The run ledger is an append-only sequence of closed, typed transitions keyed by run, wave, unit, and
candidate. Events reference evidence capsule and artifact hashes rather than embedding raw output.

Required event families:

- Plan compiled, rejected, or revised.
- Route selected and policy evidence.
- Unit queued, dispatched, terminal, remediated, cancelled, or demoted.
- Wave prepared, accepted, or failed.
- Candidate advanced, validated, reviewed, promoted, or abandoned.
- Cleanup and restart reconciliation.

Unknown event kinds fail schema validation. The ledger is not a generic event bus or telemetry dump.

### ExecutionPlan

`ExecutionPlan` is the shared intermediate representation between Terra and the runtime:

- Enumerated acceptance items.
- Ownership from each acceptance item to one or more units.
- Unit dependency DAG.
- Exact read and write manifests.
- Validation-to-acceptance coverage map.
- Shared path and exclusive resource ownership.
- Risk classes and external effects.
- Required evidence capsule hashes.
- Final coverage requirements.

Terra compiles user intent into this structure. Runtime schema and semantic checks enforce it. The
compiler does not claim deterministic understanding of natural language; it produces a typed proposal
whose missing ownership, scope, dependency, or coverage is rejected before fan-out.

### Cancellable lane lifecycle

Critical-path escalation and Failure Swarm share one bounded child lifecycle:

- Wall-clock deadline attached to the child descriptor.
- Idempotent cancellation.
- Normal process-tree termination.
- Non-interruptible commit artifact window.
- Exact worktree, gate, lease, and child-session reconciliation.
- One terminal ledger event for every launched child.
- Target branch unchanged by cancellation or cleanup.

No feature may add a second cancellation path.

### Execution policy

The execution policy is a pure, inspectable decision over `ExecutionPlan` shape and ledger aggregates.
It is not an opaque model or online learner.

Task-shape evidence may include:

- DAG width and depth.
- Language and build system.
- Validation class and duration.
- Manifest and shared-path shape.
- Luna success and Sol demotion rates.
- Integration conflict and cleanup rates.
- Matched speed and estimated cost.

Sparse or unseen shapes use the v0.8 Terra heuristic. Policy changes are versioned and recorded in the
ledger so the same input table produces the same route.

## Capability 1: Critical-path Sol Escalation

Luna remains the normal execution fabric. The runtime tracks the active dependency path currently
blocking completion. A Luna unit becomes eligible for Sol takeover when it exceeds its declared deadline
or repeats a typed implementation failure and remains on the critical path.

Escalation sequence:

1. Persist the escalation decision and evidence.
2. Cancel the Luna child through the shared lifecycle.
3. Reconcile its worktree, gate, lease, and terminal state.
4. Dispatch one Sol worker from the last accepted candidate snapshot with the same unit contract.
5. Admit the Sol artifact through the normal hidden-candidate path.

Non-critical lanes continue. At most one critical-path Sol takeover is active per run. Escalation never
changes target promotion rules.

Acceptance:

- An injected critical-path straggler is cancelled at its deadline.
- Sol completes the same bounded unit while unrelated lanes remain valid.
- The final candidate contains one accepted implementation of that unit.
- Cancellation leaves no active child, worktree, gate, or lease.

## Capability 2: Experience-driven Auto Router

The router aggregates completed ledger evidence by deterministic task shape. It compares the v0.8 Sol
and Luna choices on elapsed duration, estimated cost, demotion, and integration outcome.

The router chooses among:

- Sol serial path.
- Luna execution fabric.
- Luna fabric with critical-path Sol escalation available.

It never selects a route from model self-confidence, user-visible mode, or unpublished reasoning. Thin
samples fall back to the v0.8 heuristic. New policy versions require replay over the fixed corpus before
activation.

Acceptance:

- Every decision names its shape bucket, evidence window, policy version, and fallback reason.
- Replaying a fixed corpus produces the same routes.
- The selected policy matches or improves median speed and estimated cost versus recorded Terra choices.
- Safety failures and unknown shapes retain the existing fail-closed route.

## Capability 3: Failure Swarm

Failure Swarm activates only after the unit's normal bounded remediation fails and another canonical
validation failure remains. Available Luna lanes receive distinct read-only causal classes, for example:

- Implementation logic.
- Test assumption or fixture.
- API or type mismatch.
- Environment or configuration.
- Integration ordering.

Each lane receives the failing unit contract and declared evidence capsules. Swarm lanes cannot write,
change manifests, invoke workers, or become user-facing. Their findings become new evidence capsules.
Terra synthesizes the findings and authorizes exactly one remediation contract. There is no voting and no
candidate merge.

Acceptance:

- An injected failure produces distinct bounded causal findings.
- No swarm lane mutates source, target, manifests, or external state.
- Terra records one selected diagnosis and one remediation path.
- Duplicate findings and unchanged retries do not trigger another swarm.

## Capability 4: Acceptance Compiler

The Acceptance Compiler turns accepted user intent and bounded repository evidence into an
`ExecutionPlan` before implementation begins.

Compilation stages:

1. Enumerate observable acceptance items.
2. Map each item to owning units.
3. Fix unit dependencies and exact manifests.
4. Map validation evidence to acceptance items.
5. Assign shared paths, exclusive resources, risks, and evidence capsules.
6. Prove final coverage or return a precise compile gap to Terra.

Compilation failure is not a user blocker when Terra can gather bounded evidence or revise the plan.
Luna never repairs the compiler output itself.

Acceptance:

- Every acceptance item has unit ownership and validation coverage.
- Every mutable path belongs to an exact unit manifest and shared-path owner when required.
- Unknown dependencies, uncovered acceptance, and unowned paths fail before dispatch.
- The accepted plan feeds the v0.8 DAG without a second translation contract.

## Capability 5: Run Flight Recorder

The recorder persists Evidence Plane transitions and supports deterministic control-state replay from a
wave boundary.

Replay reconstructs:

- Accepted `ExecutionPlan` identity.
- Route and scheduler decisions.
- Unit and wave terminal states.
- Evidence and artifact references.
- Hidden candidate snapshot identity.
- Pending recovery or cleanup action.

Replay does not regenerate model output or rerun implementation. It reconstructs the durable state that
the coordinator would resume from. A replay cannot update the target.

Acceptance:

- A multi-wave run reconstructs identical typed state from the ledger prefix.
- Replay at a selected wave yields the same plan, decisions, artifacts, and candidate snapshot identity.
- Unknown, missing, reordered, or conflicting transitions fail closed.
- Ledger and replay output contain no raw logs, secrets, credentials, or Project metadata.

## Capability 6: Content-Addressed Evidence

Evidence capsules replace repeated unstructured context gathering with bounded immutable references.

Uses:

- Scout findings become capsules instead of prose copied between turns.
- Acceptance Compiler links plan items to exact evidence.
- Luna lanes receive only unit-relevant capsule hashes.
- Failure Swarm findings deduplicate by content.
- Run ledger decisions reference evidence without embedding it.
- Experience routing aggregates typed outcomes without rereading source.

Acceptance:

- Five lanes requesting identical evidence resolve one canonical capsule.
- Changed relevant source content invalidates reuse by producing a new hash.
- A unit cannot consume undeclared capsule identities.
- Capsule lookup saves repeated context reads without hiding required source from implementation.

## Version plan

### v0.8.1: Evidence Plane

- Content-Addressed Evidence store and capsule contract.
- Typed append-only run ledger referencing capsule and artifact hashes.

### v0.8.2: Plan Contract

- Acceptance item and validation coverage compilation.
- Owned DAG units, exact manifests, resources, risks, and capsule binding.

### v0.8.3: Adaptive failure runtime

- Bounded cancellable child lifecycle with deadline.
- Read-only Failure Swarm and one Terra-authorized remediation.

### v0.8.4: Replay and critical-path rescue

- Deterministic wave-boundary control-state replay.
- Critical-path Luna cancellation and one Sol takeover.

### v0.8.5: Evidence-driven routing and integrated RPT

- Inspectable experience table and deterministic Auto Router.
- Stable public contracts for `ExecutionPlan`, evidence capsules, ledger replay, route evidence, and final
  target promotion.
- Integrated clean-path and fault-path RPT.

### v0.9: Reserved

v0.9 has no assigned capability scope. Its purpose remains reserved until the complete v0.8 evidence
runtime has matched performance, cost, replay, and safety evidence. Do not move deferred v0.8 work into
v0.9 merely because a card is incomplete.

## v0.8 evidence-runtime acceptance gate

One fixed `_testenv` corpus covers a clean run, an injected validation failure, and an injected critical
path straggler.

The clean run must:

- Compile complete acceptance coverage.
- Reuse evidence capsules across five Luna lanes.
- Preserve the v0.8 speed gain with no more than 10 percent recorder/compiler wall-clock overhead.
- Validate one final hidden candidate and update the target through one CAS.

The fault runs must:

- Resolve the validation failure through one read-only swarm and one authorized remediation.
- Resolve the straggler through bounded cancellation and one Sol takeover.
- Reach terminal state faster than v0.8 behavior under the same injected fault.
- Leave no child, worktree, gate, lease, or hidden candidate leak.

Replay must reconstruct the same accepted plan, scheduler decisions, artifact references, and candidate
snapshot identity. The Auto Router must reproduce its choices over the fixed corpus and retain the v0.8
fallback for sparse shapes. Target corruption, partial promotion, stale-target overwrite, secret exposure,
or unreplayable accepted state is a release blocker.

## Non-goals

- Generic agent teams, social personas, voting, or agent-to-agent conversations.
- Online machine learning or an opaque route score.
- Replay of model reasoning or raw model transcripts.
- Full-source duplication inside capsules or the run ledger.
- OS-level process isolation beyond normal process-tree termination and fail-closed cleanup.
- Parallel target writes, partial target acceptance, or automatic stale-target rebase.
