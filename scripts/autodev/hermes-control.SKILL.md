# Autodev owner replies

Use when the owner replies `autodev <project>: <instruction>` or explicitly refers to an autodev notification.

Runner: `/home/user/Sortie-dogs/scripts/autodev-runner.mjs`.
Node: `/home/user/.local/bin/node`.
Configurations:
- `sortie-dogs-dev23`: `/home/user/Sortie-dogs/scripts/autodev/sortie-dogs.json`.
- `vibe-dev-mate-kanban`: `/home/user/Sortie-dogs/scripts/autodev/vibe-dev-mate.json`.

1. Read the selected configuration and run `node <runner> status --config <configuration>` using the exact Node path. Read the latest evidence and reported blocker before any change. If project identity is ambiguous, ask which project; do not operate both by guess.
2. An informational reply is not a resume. Answer status questions from retained evidence. To forward an explicit authorized continuation or correction, save the owner's verbatim instruction under the configured state root, with date and the originating reply identity where available, then run `node <runner> resume --config <configuration> --instruction <absolute-file>`. Do not add another developer session, cron job or mirror board. The existing cron dispatches the next unit. Report the command exit and retained Session ID, then confirm actual admission from state/events; a successful resume command is not completion.
3. Maintain the current scope and host permissions. Do not automatically answer native OpenCode permissions/forms; link the pending Session and ask the owner to answer in OpenCode. Never invent approval from an unrelated reply. The runner's `pause` stops future dispatch, not active native work; explain that distinction when asked to stop.

No further budget increase, attempt replay, global apply, publish or release without applicable explicit authorization. Use the runner's `reconcile --execute` only for a specifically requested evidence-backed accounting repair; preserve the receipt and original artifacts.

The initial approval was implementation 0, one readonly Astra review maximum (including failed/uncertain delivery), existing ChatGPT OAuth only. The owner later authorized inlet/acceptance changes only for user-visible product behavior, never verification-only scaffolding or test-purpose modifications. Inspect `notification-state.json` and `notification-events.jsonl`: direct delivery requires the native send receipt's success and message ID, bound to the current cron execution. A local/suppressed cron result neither confirms nor negates that direct send. Never describe emitted, skipped, queued or unknown delivery as delivered.
7. Every user-facing progress report, question and reply must be a Japanese summary of at most five lines. Use current outcome, actual blocker/question, next operation and current API-equivalent exposure only. Never paste English handoff prose, old budget blockers, hashes, long paths, Session IDs or diagnostic JSON. Keep full technical evidence in the retained files. Do not invoke another model/review just to translate or shorten a notification.
8. Distinguish transport success from the owner having seen a notification. If the owner reports a missing notice, inspect the actual target/receipt and intentionally resend the current concise blocker with a new retained receipt. For required UI operations, explicitly say whether the owner or coordinator must act. Native Session worktree moves retain Session identity and the canonical campaign; do not create a replacement controller or move the Session back merely to satisfy the monitor.
9. No-agent cron does not load this chat skill. The shared runner's Vibe `autonomy.instruction_files` passes retained f/g/h authority to every native work unit. It follows evidenced local work despite deferred external steps and performs at most one ambiguous-blocker reconsideration per stable card/authority in the same coordinator, with no extra review/model/controller. Inspect `standing_authority`, `autonomous_reconsiderations`, `work_id` and `pause_origin` instead of repeatedly issuing manual resumes. Owner pauses, native permissions/authentication failures, exhausted budgets, ambiguous submissions, consumed product attempts and actual local-work exhaustion are not automatically overridden.
